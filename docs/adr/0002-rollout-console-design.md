## 2. 決策驅動因素

1. **避免誤操作造成大規模升級**：一次送出可能影響上萬台主機。對象、批次、時段要能在送出前一次看清楚，數字要與確認字串一致，而且送審摘要寫的必須是實際會發生的事。
2. **權責分離**：開啟雙人覆核時，第二個人必須對「被固定下來的內容」做出確認，而且這個確認**由伺服器強制**，不能只存在於畫面上。一個主控台使用者不能獨自繞過。
3. **可稽核**：送出、核准、退回、逾時、關閉雙人覆核都要留下紀錄；稽核員不需要讀設定檔就能知道目前的政策與它何時改變。
4. **與既有畫面一致**：沿用設計包的畫面編號、確認等級（L1～L3）、伺服器計算的確認字串、三段式錯誤文案、狀態詞彙與計數泡泡規則。
5. **可及性**：WCAG 2.1 AA、axe 0 違規（淺色與深色）、全部可用鍵盤操作；狀態不能只靠顏色；即時更新用 `aria-live`。只支援 Chromium 系（D44）。
6. **實作成本**：主控台是原生 ES modules、沒有框架，嚴格 CSP 與 Trusted Types；優先重用既有的欄位與預覽。
7. **API 相容**：0.9 的用法（省略 `waves`、`schedule`）不能變。雙人覆核尚未發佈，核准 API 的請求內容可以在 0.10.0 之前修改。
8. **與其他 ADR 的相容**：ADR-0001（Windows 的 `slot` 安裝方式）與 ADR-0003（`rollback_bundle`、本機封存）會改變資格分類與「無法自動回滾」的定義；本文件的畫面不能把目前的原因與機制寫死（決策點 8）。

## 3. 決策點與方案

### 決策點 1：建立推送的形式、草稿的儲存與修改

**1a. 表單的形式**

| 方案 | 說明 | 優點 | 缺點 |
|---|---|---|---|
| A. 維持單頁表單加區塊 | 現況 | 不用改；一眼看到全部 | 0.10 之後有 30 個以上的欄位；最容易出錯的「對象」與「批次」沒有被分開檢查；與設計包「0.10 改為精靈」不符 |
| B. 分步精靈 | 四步，最後一步是唯讀的檢視與送出 | 每一步只回答一個問題；最後一步的摘要也正好是核准者要看的內容，可以共用同一個元件 | 重構成本；步驟間切換要處理驗證與焦點 |
| C. 單頁＋區塊導覽＋固定摘要 | 單頁保留，加錨點與固定摘要 | 成本最低 | 沒有「檢視」這個強制停頓點 |

**建議：B**（`REMOTE.md` 第 9 節 R6 是五步；建議把「目標版本」與「對象」合併，因為資格分類同時取決於兩者）：

| 步驟 | 內容 | 這一步的預覽 |
|---|---|---|
| ① 版本與對象 | 名稱、目標版本（`breaking` 的勾選、`min_kairos` 不相容的 `KRS-W8415`、版本庫檔案有問題時的警告）、對象（全部，或群組／標籤／主機的聯集與排除）、選項「允許無法自動回滾的主機」「允許降版」 | 資格預覽：可升級 N 台，不會升級的依原因分列、每類可展開前 100 台；重疊的推送 |
| ② 批次 | 決策點 3 的批次編輯器、同時升級的上限、健康確認期限、離線寬限 | 每批的台數與累計 |
| ③ 時段 | 決策點 4：開始與結束時間、每週時段、時區；都不填＝立即開始、隨時可升級 | 現在是否在時段內、下一個時段 |
| ④ 檢視與送出 | 唯讀的**送審摘要**（決策點 2b）；啟用雙人覆核時寫明誰可以核准 | 「送出推送…」開啟 L2／L3 對話框（確認字串由預覽的 `confirm_text` 提供，伺服器驗證，不變） |

互動規則：

- 路由：`/pulse/rollouts/new` 與 `/pulse/rollouts/:id/edit`，步驟以查詢參數 `?step=1…4` 表示。
- 步驟列是 `<nav aria-label="建立推送的步驟">` 內的有序清單，目前的步驟 `aria-current="step"`；已完成的步驟可以點回去，尚未到達的不能跳過（`aria-disabled` 並說明原因）。修改既有草稿時四步都可以直接進入。
- 「下一步」時驗證這一步：有錯誤時在步驟頂端顯示錯誤摘要（`role="alert"`，逐項連到欄位）並把焦點移到摘要；切換步驟後焦點移到步驟標題。
- 預覽沿用 600 ms 防抖與 `aria-live="polite"`；預覽失敗時保留上一次的結果並標示「預覽不是最新的」。
- 步驟 ④ 進入時一定重新取一次預覽；與上一次的數字不同時顯示差異。
- 設計系統是否已有通用的步驟列元件：我以關鍵字搜尋 `design/design-system/README.md` 沒有找到〔設計包〕；需要設計包補上或指出既有的規格（第 6.1 節 #2）。

**1b. 草稿的儲存**

| 方案 | 說明 | 評估 |
|---|---|---|
| A. 只在送出時建立（現況） | — | 填到一半離開就全部遺失；被退回的推送無法修改 |
| B. 明確的「儲存草稿」 | 每一步都有「儲存草稿」；第一次 `POST`、之後 `PUT`；離開未儲存的精靈時詢問 | 行為可預期；稽核事件少 |
| C. 自動儲存 | 每次切換步驟自動 `PUT` | 大量 `rollout.update` 稽核事件與無名草稿 |

**建議：B**，並在步驟 ④ 按「送出推送…」時先自動儲存。草稿不固定對象、也不算在「未結束的推送」中。

**1c. 修改與樂觀鎖**

- 入口：詳情頁在 `draft`、`pending_approval`、`scheduled` 狀態顯示「修改…」（`rollouts:write`）。
- `draft`：直接進入精靈；被退回或逾時退回的草稿在精靈頂端顯示原因。
- `pending_approval`、`scheduled`：先以 **L1** 確認「修改會把推送退回草稿：已固定的對象會清除，需要重新送出（並重新核准）」；實際的退回發生在第一次儲存時（`PUT`）。
- **樂觀鎖（修改功能的必要條件，不能分開出貨）**：兩位管理員同時修改同一份草稿時，後寫的會無聲地蓋掉先寫的；在雙人覆核下這表示送出的內容可能不是送出者以為的內容。

  | 方案 | 說明 | 評估 |
  |---|---|---|
  | A. 本文欄位 `expected_updated_at` | `PUT` 的本文帶上讀到的 `updated_at`；不符時 409 `rollout_modified`（`details.updated_at`、`updated_by` 若有記錄） | 與這套 API 既有的做法一致：前置條件都放在本文（`impact_token`、`confirm`、設定檔回復的 `revision`）；`kairos/src/api/` 的 JSON 資源沒有任何一個使用 `ETag`／`If-Match`（只有靜態檔的 `If-None-Match`）〔程式〕 |
  | B. HTTP `If-Match` | `GET` 回 `ETag`，`PUT` 帶 `If-Match`，不符時 412 | HTTP 的標準語意；但要為這一個資源引入新的標頭慣例、新的狀態碼（412）與錯誤對照 |

  **建議：A**。外部審查偏好 B；我保留 A 的理由是一致性與成本，兩者在安全上等價。實作注意：`RolloutSpec::parse` 會拒絕不認得的欄位，`expected_updated_at` 要在 handler 先取出。主控台在 409 時顯示「這份草稿已在 10:32 被修改」並提供「重新載入」（不提供強制覆寫）。
- **放棄草稿**：API 沒有刪除，草稿以取消結束並留在「已取消」（保留稽核的對象）。建議草稿的對話框標題為「捨棄草稿」、原因選填（後端對 `draft` 放寬）；待決事項 U7。

### 決策點 2：雙人覆核

**2a. 待核准清單放在哪裡**

| 方案 | 說明 | 評估 |
|---|---|---|
| A. S26 清單的檢視 | 檢視切換：進行中（預設）／待核准／草稿／已結束／全部，各附計數（與 S06 的檢視同一種樣式） | 不新增頁面與路由 |
| B. 獨立的「待核准」頁 | SideNav 另一個項目 | 與註冊的 S13「待核准」同名 |
| C. 併入 S13 | 與註冊申請放在同一個清單 | 權限、欄位、操作完全不同 |

**建議：A**。「待核准」檢視（`/pulse/rollouts?view=pending_approval`）的欄位：名稱、目標版本、可升級台數、送出者、已等待多久（與核准期限）、風險標示（降版、無法自動回滾、一次全部）、「我可以核准」。

**計數泡泡**

- SideNav「升級推送」泡泡：已暫停＋未處理的回滾失敗＋**目前使用者可以核准的**待核准推送。
- 「可以核准」**由後端計算**：清單 `meta` 新增 `pending_approval_actionable`（依這次請求的 principal：有 `rollouts:approve`、是帳號登入的工作階段、不是該推送的建立者或送出者）。不由主控台以帳號字串比對——身分的格式與規則（例如之後的服務帳號）只應該存在一處。`meta.pending_approval`（總數）保留。
- 可存取名稱要寫出組成，例如「升級推送，2 個等你核准、1 個已暫停」。`design/kairos/ia.md` §7 補上這一列。

**2b. 核准的確認：L2，由伺服器計算與驗證**

現況的核准 API 不接受任何確認：任何有 `rollouts:approve` 的工作階段都可以用空的本文核准〔程式〕。只在畫面上要求輸入字串**不構成**第二人的確認——這是安全邊界，不是可以漸進補上的介面功能。

| 操作 | 方案 | 建議 |
|---|---|---|
| 核准 | L1（現況）；或 **L2**：輸入「核准 N 台」（N 為已固定的可升級台數） | **L2，且伺服器驗證是出貨的前置條件**。包含降版時為 L3 字串「核准降版 N 台」＋原因必填，依 1.1 的定案不重新驗證密碼 |
| 退回 | L1，原因必填（現況） | 維持。退回往安全的方向 |

**送審摘要與它的摘要值（digest）**

- 送出（`submit`）時對象已固定。伺服器為這次送審產生 **`submission`** 物件，放在推送的 JSON（`pending_approval` 時才有）：

  | 欄位 | 內容 |
  |---|---|
  | `digest` | 這次送審內容的 SHA-256：正規化後的推送內容（目標版本、選擇條件、批次、時段、選項）＋已固定的主機清單（`agent_id`、批次、資格分類，依固定的順序）＋`submitted_at`、`submitted_by`。內容或對象有任何改變，`digest` 就不同 |
  | `confirm_text`、`confirm_level` | 「核准 N 台」／「核准降版 N 台」；`L2`／`L3`。由伺服器依 `rollout_hosts` 計算（與 `submit` 的 `rollout::confirm_text` 同一套算法） |
  | `eligible`、`downgrade`、`no_rollback`、`skipped`（原因 → 台數）、`waves`（每批台數） | 摘要的數字 |
  | `warnings[]` | 固定代碼的風險提醒（`single_wave`、`large_first_wave`、`no_pause_between_waves`、`downgrade`、`no_rollback`、`artifact_problem`…），主控台組文案 |
  | `approvers_available` | 目前可以核准這個推送的使用者數（見 2g） |
  | `approval_deadline` | 核准期限（見 2e；沒有逾時時 `null`） |

- **核准的請求**：`POST …/approve` 的本文為 `{ "confirm": "核准 1,520 台", "digest": "…", "reason": "…" }`。伺服器在**同一個交易**中：重新讀取推送與 `rollout_hosts`、重新計算 `digest` 與 `confirm_text`、比對請求、檢查狀態／身分／期限／檔案（決策點 5），全部通過才轉移狀態。
  - `confirm` 不符（空字串、舊的台數、降版時用了非降版的字串）→ 400 `confirmation_required`（`details.confirm_text`、`confirm_level`，與 `submit` 相同）。前後空白比照 `submit` 以 `trim` 處理後比對。
  - `digest` 不符（核准者看到摘要之後推送被改過）→ 409 `submission_changed`，主控台重新載入摘要。
  - 降版而沒有 `reason` → 400。
- 稽核 `rollout.approve` 的 `details` 記下 `digest` 與台數，之後可以證明核准者核准的是哪一份內容。
- **大量主機**：摘要顯示完整的總數與各分類的台數；每類可展開前 100 台；另提供「匯出完整清單（CSV）」（以既有的 `GET /api/v1/rollouts/{id}/hosts` 分頁取回）。核准者不需要逐台看過，但要能取得完整清單。
- 核准時 `starts_at` 已經過了：對話框明寫「核准後會立即開始升級」。`ends_at` 已過（409 `schedule_ended`）：就地說明並建議退回。

**2c. 身分限制的三人邊界（明確決策）**

實作禁止建立者**與**送出者核准〔程式：`engine.rs` 第 632～640 行〕。結果是：甲建立草稿、乙修改並送出時，甲和乙都不能核准，**必須有第三位管理員丙**。文件多處寫的「另一位管理員」在這個情境下不成立，只有兩位管理員的部署會卡住。

| 方案 | 規則 | 評估 |
|---|---|---|
| A. 維持現況 | 建立者與送出者都不能核准 | 最保守、已實作並有測試；規則容易說明（「建立或送出的人不能核准」）。代價是上述的三人邊界；兩位管理員的部署要由同一個人建立並送出，另一個人核准 |
| B. 只排除送出者 | 送出者（做了 L2 確認、固定對象的人）不能核准；沒有送出的建立者可以 | 仍然是兩個不同的人各做一次確認；兩位管理員的部署不會卡住。要改後端與測試，並放寬一條已寫進 CHANGELOG 草稿的規則 |

**建議：A**（0.10.0 不改行為），但把邊界明確化：

- 精靈步驟 ④、送出對話框、待核准的詳情頁都寫出「誰可以核准」：「需要由 chen.y（建立者）與你（送出者）以外、有核准權限的管理員核准。」
- 送出前若 `approvers_available` 為 0（見 2g），在步驟 ④ 就警告，而不是送出之後才發現。
- 兩位管理員的部署在說明文件中寫明：由同一人建立並送出。
- 補充：修改者（`PUT` 的人）目前不在排除之列；推送是否記錄最後修改者我沒有確認（第 10 節）。在方案 A 下這不造成漏洞（修改會退回草稿，內容由送出者重新確認並負責），但「碰過內容的人都不能核准」並不是實際的規則，文案不要這樣寫。
- 列為待決事項 U11；測試見第 7.4 節 A3。

**2d. 送出者與核准者看到的差異**（詳情頁，`pending_approval`）

| | 送出者／建立者 | 可以核准的人 | 維運者、稽核員 |
|---|---|---|---|
| 頁首狀態 | 「待核准」＋「已在 11/12 10:05 送出，等待另一位管理員核准（期限 11/19 10:05）」 | 「待核准」＋「chen.y 在 11/12 10:05 送出，等待核准」 | 「待核准」＋送出者與時間 |
| 主要動作 | 「修改…」「取消推送…」「複製連結」 | 「核准…」（主要）「退回…」 | 無 |

**2e. 逾時未核准**

現況沒有逾時：待核准的推送無限期佔住它的主機（其他推送會 `rollout_overlap`〔程式〕），而且核准的是幾天前固定下來的對象。

| 方案 | 說明 | 評估 |
|---|---|---|
| A. 不逾時，只顯示等待時間 | 清單與詳情顯示「已等待 3 天」；超過 72 小時在 S20「遠端管理」列為警告 | 不用改引擎；過期的對象仍可能被核准 |
| B. 逾時自動退回草稿 | 見下方的完整語意 | 釋放主機、強迫以新的對象重新送審 |
| C. 逾時自動取消 | 同 B 但轉為 `cancelled` | 建立者要從頭再建一次 |

**建議：B；在 B 出貨之前先做 A 的顯示。B 必須與通知（2f）一起出貨**——只靠泡泡時，逾時很容易變成「沒人注意到 → 七天後自動退回 → 重新送出 → 再退回」。

**B 的完整語意**

- **設定**：`[remote] rollout_approval_timeout_hours`，預設 168，範圍 1～720，`0` 表示不逾時。沿用 `config/remote.rs` 的模式：範圍以常數定義、在 `validate()` 檢查〔程式：`MAX_ROLLOUT_RETENTION_DAYS` 的做法〕；納入叢集「需要一致的設定」的雜湊。需要重新啟動才生效。
- **期限在送出時固定**：`submit` 進入 `pending_approval` 時把 `approval_deadline = submitted_at + timeout` 寫進推送（新欄位；`0` 時為 `NULL`）。之後修改設定**不影響已經送出的推送**：改小不會讓舊的推送立刻過期，改大或改為 `0` 也不會延長。理由：期限已經顯示給送出者與核准者，不應該因為重新啟動而改變；稽核也能看到每一次送審當時的期限。要讓舊的推送套用新的期限，退回後重新送出即可。
- **轉移等同由 `system` 執行的退回**，在單一交易中：重新讀取推送 → 仍是 `pending_approval` 且 `approval_deadline <= now` → 刪除 `rollout_hosts`（釋放 `rollout_overlap`）→ 清除 `submitted_at`／`submitted_by`／`approved_at`／`approved_by`／`approval_deadline` → 狀態 `draft` → 寫稽核 → 提交。與人工退回（`engine.rs` 第 693～704 行）用同一段程式。
- **原因以穩定的代碼保存**，不保存中文句子：新欄位 `reject_cause`（`rejected`＝人工退回、`approval_expired`＝逾時；再次送出時清除）。人工退回時 `reject_reason` 是使用者寫的原因；逾時時 `reject_reason` 為 `NULL`，主控台依 `reject_cause` 組出文案（「超過核准期限（11/19 10:05）沒有核准，已自動退回草稿」）。
- **稽核**：`rollout.approval_expired`，執行者 `system`；`details`：`rollout_id`、`name`、原本的 `submitted_by`、`submitted_at`、`approval_deadline`、`timeout_hours`、固定的主機數、`digest`。
- **期限是權威，不是引擎的檢查時間**：核准的交易也檢查 `approval_deadline`；已過期時回 409 `approval_expired`，即使引擎還沒來得及退回。因此結果不取決於「核准的請求與引擎的那一輪誰先到」。
- **競態**：核准、退回、修改、取消、逾時都在交易內先檢查狀態再轉移，**只有一個會成功**，其餘得到 409 `invalid_state`（或 `approval_expired`）。SQLite 是單一寫入者；PostgreSQL 後端需要以條件式更新（`UPDATE … WHERE state = 'pending_approval'` 並檢查影響的列數）或列鎖達成同樣的保證——整合分支的 PostgreSQL 實作是否已如此，需要確認（第 10 節）。重複的請求不具副作用：第二次核准得到 409。
- **誰執行**：推送引擎（每 5 秒一輪；叢集中只有主節點）。Kairos 啟動後沿用既有的「1 分鐘內不提議」的保護期，保護期過後補做停機期間到期的退回；稽核事件的時間是實際處理的時間，`details.approval_deadline` 是原本的期限。
- **系統時間**：以牆上時鐘判斷（與排程、時段相同）。時間往前跳會提早退回（往安全的方向）；往後跳會延後。不另外處理，寫入文件。
- **`rollout_approval` 改為 `none` 之後**：已在 `pending_approval` 的推送仍要核准或退回，期限照常適用。
- **已排程的推送**（已核准、等待 `starts_at`）不受逾時影響。

**2f. 通知**

| 方案 | 說明 |
|---|---|
| A. 泡泡＋「複製連結」 | 送出後的畫面與待核准的詳情頁提供「複製連結」，由送出者自行告知 |
| B. 系統規則「升級推送等待核准」 | 沿用既有的遠端管理系統規則的做法（`sys.rollout_paused` 等，`kairos/src/alerts/rules.rs`〔程式〕）：推送進入 `pending_approval` 時開事件（資訊等級、**預設不推播**、可以接到通知管道）；核准、退回、取消、逾時時結束。距離期限 24 小時仍未核准時升為警告 |

**2g. 沒有可核准者的偵測**

`approvers_available`：啟用中、有 `rollouts:approve`、不是這個推送的建立者或送出者的本機或已知目錄帳號數，由後端計算。

- 預覽（建立時以目前的使用者為準）與 `submission` 都回傳。
- 為 0 時：步驟 ④ 與送出對話框警告「目前沒有其他可以核准的管理員：送出後會一直停在待核准」（不阻擋——之後可能新增帳號）；待核准的詳情頁與「待核准」檢視標示；S20「遠端管理」列為警告。
- 待核准期間可核准者被停用或撤銷權限時，數字隨之改變（每次讀取時計算）。
- 目錄服務（LDAP）中從未登入過的使用者不會被計入，文案用「目前已知」。

**2h. 退回原因與覆核紀錄**

- 退回原因必填、1～500 個字元，寫入稽核 `rollout.reject`，在草稿的頁首與精靈頂端顯示，再次送出時清除（現況）。
- 詳情頁新增「覆核紀錄」：目前這一輪的送出者／時間、期限、核准者／時間或退回（含逾時）與原因。完整的多輪歷史在稽核日誌；對有 `audit:read` 的人提供「在稽核日誌查看」。

**2i. `rollout_approval` 的呈現，以及 `required` → `none`**

**這是一個治理缺口，本文件不宣稱它等同 L3。** 修改 `kairos.toml` 需要主機上的系統權限，但「權限高」不等於「兩個人」：一位有主機權限的人可以獨自把政策關掉、重新啟動，然後以單人送出大型推送。主控台內的雙人覆核能防的是「單一的主控台管理員」，防不了主機的系統管理者（他也可以直接改資料庫）。能做的是：**讓關閉這件事無法安靜地發生**，並把「誰可以改設定檔」這一段交給部署端的流程。

| 方案 | 說明 | 評估 |
|---|---|---|
| A. 只在設定檔修改；S21 唯讀；啟動時偵測改變並發出高可見度的事件 | 見下方 | 成本低；不阻止單人關閉，但一定留下紀錄並通知 |
| B. 可從主控台修改 | 設定存資料庫、立即生效；`none` → `required` 為 L1，`required` → `none` 為 L3 且本身需要另一位管理員核准 | 才是真正的權責分離；需要 L3 的重新驗證、「設定變更的待核准」流程、以及設定檔與資料庫優先順序的處理（否則設定檔仍可繞過） |
| C. 維持現況 | 只在 S20 的 `values` | 政策被關閉時沒有任何紀錄 |

**建議：0.10.0 採 A，並明列為接受的治理缺口；B 列為後續**（待決事項 U5）。核定後必須修訂 `REMOTE.md` 第 5.4 節（目前寫「是 L3 操作」），不能只改設計包的文案。

**A 的內容**

- **S21**：「連線與安全」分頁新增「遠端管理」卡片，列出 `[remote]` 的鍵。資料已經在 `GET /api/v1/settings` 中〔程式〕，**不需要新增後端**，只要在 `TAB_SECTIONS` 加上 `remote` 與對應的字串。`rollout_approval` 顯示為「雙人覆核：需要／不需要」、來源（設定檔／環境變數／預設）、「在 kairos.toml 修改，需要重新啟動」，以及上一次改變的時間（下述的紀錄）。
- **前值的保存位置**：資料庫（隨備份與叢集共用），記錄 `value`、`source`（`file`／`environment`／`default`）、`observed_at`、觀察到它的節點。放在哪一張表由工程決定（既有的 `settings` 表存的是主控台的覆寫值，語意不同，不建議混用）；需要一個小的 schema 變更，與 2e 的兩個欄位併入同一次遷移。
- **啟動時的比對**（叢集中只由主節點寫入；`rollout_approval` 已納入「需要一致的設定」的雜湊，節點之間不同時另有 `KRS-W8505`〔整合分支：`kairos/HA.md` 第 722 行、`cluster/confhash.rs`〕）：

  | 情況 | 處理 |
  |---|---|
  | 沒有前值（升級到有這個功能的版本後第一次啟動、全新安裝） | 記下目前的值作為基準，稽核 `settings.rollout_approval.baseline`。不發警告——**但**若目前是 `none` 而資料庫裡有曾經送審或核准過的推送（`approved_at` 不是空的，或有 `pending_approval` 的推送），表示這台 Kairos 曾經啟用過雙人覆核：視同 `required` → `none` 處理 |
  | 前值與目前相同 | 不寫事件 |
  | `none` → `required` | 稽核 `settings.rollout_approval.change`（`from`、`to`、`source`）；資訊 |
  | `required` → `none` | 稽核同上；**另開警告等級的告警事件**（下述） |
  | 只有來源改變（例如由設定檔改為環境變數） | 稽核同上，`details.source_changed` |
  | 還原資料庫備份 | 前值是備份當時的值。與目前的設定不同時照上列處理；事件文字寫「與資料庫記錄的上一次設定不同」，不寫「剛剛被修改」。這可能把還原前就做過的修改再報一次——寧可重複 |
  | 資料庫遺失、換成新的資料庫 | 等同「沒有前值」；此時沒有歷史可以判斷，是這個做法的已知限制 |
- **寫入時點**：在遠端管理服務開始接受請求（主控台 API 與推送引擎）**之前**完成比對與稽核寫入。寫入失敗時遠端管理不啟動（主控台回 503 `remote_unavailable`），其餘功能照常——不能在沒有記錄的情況下以新的政策接受推送。
- **事件的嚴重度與通知**：`required` → `none` 開系統規則「雙人覆核已關閉」的事件，**警告等級、預設推播**（不是資訊等級的紀錄事件），對象是管理員與稽核員；事件不會自動結束，需要有人確認。S20「遠端管理」列與 S26 清單頁首在 30 天內顯示「雙人覆核已在 11/12 14:03 關閉（設定檔）」。
- **事件只留在同一台 Kairos 上的侷限**：能改設定檔的人通常也能動這台機器上的紀錄。事件的價值取決於它有沒有離開這台機器——通知管道（Email、Webhook）與稽核的外送。部署文件要寫明：啟用雙人覆核的單位應該把這條規則接到通知管道。
- **部署端的補償措施**（寫入 `kairos/packaging/INSTALL.md` 與 `REMOTE.md` 第 5.4 節；這些是部署單位的責任，Kairos 不強制）：
  1. `kairos.toml` 納入設定管理（Git、Ansible 等），修改需要經過另一個人審核（PR 雙簽）。
  2. 主機上的特權操作經過 PAM／sudo 的核准或側錄流程；限制誰可以重新啟動 Kairos 服務。
  3. 對 `kairos.toml` 設檔案完整性監控（auditd、AIDE 等）。
  4. 把「雙人覆核已關閉」接到通知管道，稽核日誌外送到 Kairos 以外的系統。
- 由 `required` 改回 `none` 之後，已經在 `pending_approval` 的推送仍然要核准或退回〔程式：核准只看推送的狀態〕。

### 決策點 3：自訂批次的編輯器

| 方案 | 說明 | 評估 |
|---|---|---|
| A. 逐批的欄位列 | 每批一個 `fieldset`：大小（「%」或「台」）、上限台數、觀察時間、失敗上限、人工繼續；最後一批固定為「其餘」 | 與 API 一一對應；可及性最單純 |
| B. 拖曳的比例條 | 以滑桿切分 100% | 百分比是「當時剩餘」而不是總數，比例條會誤導 |
| C. 只提供範本 | 兩批／四批擇一 | 不符合已實作的能力 |

**建議：A**：

- **範本**：兩批（預設）、建議的四批（1% → 10% → 50% → 其餘），取自預覽的 `wave_templates`。套用會取代目前的批次，已經手動改過時先確認（L1）。
- **第一批**稱為「先行批次」。來源：「自動挑選」或「指定主機」（`canary_agent_ids`，`Combobox`，只能選可升級的主機）。只有一批時不提供指定主機。
- **大小**：數值＋單位。百分比的說明：「以這一批開始時**剩餘**的可升級主機計算，至少 1 台」。每一列顯示預覽算出的結果：「152 台（剩餘 1,520 台的 10%）· 累計 168 台」。
- **觀察時間**以分鐘輸入（0～10,080）並顯示換算；**失敗上限**以百分比輸入；**人工繼續**為核取方塊。
- **增減**：「新增批次」插在「其餘」之前，最多 `max_waves` 批；每批有「移除第 N 批」。不提供拖曳排序。
- **驗證（阻擋）**：數值範圍；批數；指定的先行主機不在可升級名單中。
- **提醒（不阻擋）**：只有一批；第一批超過 10% 或 100 台；批次之間沒有停頓；某一批算出來是 0 台。這些提醒**由伺服器在預覽與 `submission.warnings[]` 以固定代碼回傳**，精靈、送審摘要與核准對話框顯示同一組，不由主控台各自推算。
- **批次摘要**：以文字清單列出每批的台數與參數；比例條只作輔助（`aria-hidden`）。

### 決策點 4：時段

**4a. 用語（待決，研究中）**

推送的時段是「允許**開始**替換的時間」，告警的「維護時段」是靜音；兩者目前同名。候選：(a) 維持「維護時段」並在說明中區分；(b) 推送改稱「升級時段」；或其他名稱。**這一項目前另外交給兩個外部模型研究中，結果另附；本次修訂不定案**（待決事項 U4）。本文一律寫「時段」；實作時字串集中在一處，定案後一次替換。無論採用哪個名稱，都必須在 0.10.0 發佈前決定。

**4b. 時區選擇（IANA）**

- 元件：`Combobox`，可輸入搜尋。清單最上方固定：Kairos 的預設（預覽的 `default_timezone`）、`Asia/Taipei`、`UTC`。
- **可選的名稱由伺服器提供**（預覽或另一個端點回傳伺服器接受的時區清單與 tzdb 版本），不使用瀏覽器的 `Intl.supportedValuesOf('timeZone')`——瀏覽器與伺服器的時區資料庫版本可能不同，使用者會選到伺服器不接受的名稱。tzdb 的來源與版本由 IANA 支援的那條線決定，是本項的前置條件。
- 顯示依 `copywriting.md` §5.1：`Asia/Taipei（UTC+8）`。有日光節約時間的時區另加說明。
- 既有以固定位移建立的推送照原樣顯示，修改時可以保留。
- 預設值：Kairos 的預設時區。不採用瀏覽器的時區（§5.1）。
- **`starts_at`／`ends_at` 以同一個時區輸入**，欄位標籤帶時區；清單與詳情仍依全站的顯示時區，不同時在時段摘要後註明時段的時區。
- 換季當天不存在或重複的當地時間如何解讀，由工程（IANA 那條線）定義；現有程式只支援固定位移〔程式〕，本文件不對此做任何主張。

**4c. 每週時段的編輯**

| 方案 | 說明 | 評估 |
|---|---|---|
| A. 時段列 | 每個時段一個 `fieldset`：星期、開始、結束 | 現況；看不出一週的全貌 |
| B. 7×24 的格子 | 以滑鼠塗選 | 鍵盤操作困難、無法表達任意的 `HH:MM` |
| C. 時段列＋唯讀的一週總覽 | A 加上依星期排列的文字總覽 | 保留 A 的優點並補上全貌 |

**建議：C**：

- 星期提供「每天」「平日」「週末」；一個都沒勾視為每天（API 的行為），介面上直接顯示為「每天」。
- 結束早於開始時標示「跨午夜：到隔天 05:00 為止（算在開始的那一天）」。開始與結束相同為錯誤。
- 最多 16 個時段；相連或重疊的時段在總覽中合併顯示並提示。
- 一週總覽是文字清單，與送審摘要、詳情頁使用同一段文字。
- **阻擋**：`ends_at` 早於開始或早於現在；排程中已經沒有任何可用的時段（現況只警告，建議改為不能進入步驟 ④）。
- **提醒**：每個時段都短於 30 分鐘。

**4d. 目前是否在時段內**

- 步驟 ③ 與送審摘要：一行狀態文字（`role="status"`）——「現在在時段內，到今天 05:00 為止。」「現在在時段外，下一個時段是 11/14（六）01:00。」
- 沒有設定時段時：「沒有限制時段：送出（核准）後隨時可以開始升級。」

**4e. 時段外的推送狀態文案**

- 推送的狀態維持「進行中」，不新增狀態、也不借用「已暫停」。「下一步」欄與詳情頁首：「等待時段 · 11/14（六）01:00 開始（還有 3 小時 12 分）」；之後沒有時段時以警告樣式顯示。
- 已排程：「已排程 · 11/15 01:00 開始」。
- 主機層級：`pending`＋`window_closed` →「未開始（等待下一個時段）」；超過 10 次 →「已逾期（連續 10 個時段都沒有開始）」並提供「重試」；`expired`＋`rollout_ended` →「已逾期（推送已到結束時間）」。
- 時段結束時還在替換中的主機照常完成，詳情頁以一行資訊說明。

**建議正式分配為 `KRS-W8417`（號碼不變）**

- 子類別 84「遠端升級」；只有 Kairos 端，不鏡像；等級 W。
- 「檔案不存在」與「大小不符」同號，以「原因」區分（比照 §29.4 #3）。
- 三段式草稿：
  - 標題：Pulse 版本庫的檔案遺失：0.9.0 的 pulse-0.9.0-…-amd64.deb（影響 312 台主機）
  - 原因：版本庫記錄這個發佈檔已經存入，但在 `data/releases/` 找不到它（或大小與記錄不符）。常見的原因是還原了備份——`kairos db backup` 不包含發佈檔——叢集換手後接手的節點沒有這個檔案，或檔案被手動移動、刪除。補回之前，需要這個檔案的主機無法升級或回滾。
  - 處理方式：
    1. 取得同一個版本的官方發佈包，在「Pulse 版本庫」這個版本的詳情按「上傳發佈檔…」重新上傳（或執行 `kairos releases import <目錄>`）；只需要補上遺失或大小不符的檔案。
    2. 不再需要這個版本時可以刪除它（沒有推送使用、也不是任何主機的回滾目標時）。
  - 技術細節：`file_problem`（`missing`／`size_mismatch`）、預期的路徑 `<releases_dir>/<sha256>`；只檢查檔案是否存在與大小，不重算雜湊。
  - 呈現：S20「遠端管理」列、S25 頁首與檔案標記、S26 的資格預覽與 `next_action`、`kairos releases list`。
- 標題括號內的「影響 N 台主機」刻意不寫「回滾需要」：這個數字的定義會隨 ADR-0003 改變（決策點 8）。

**一併請設計包處理的既有代碼**

- `KRS-E6106`：說明與三段式改為「不能核准自己**建立或送出**的推送」（依 U11 的結果）。
- 新的 API 錯誤（`submission_changed`、`approval_expired`、`artifact_missing`、`rollout_modified`、`session_required`）：建議都不分配新的產品代碼，在 `copywriting.md` §3.4 的對照註明「不對應產品代碼，主控台以一句話就地說明」；`artifact_missing` 附 `KRS-W8417`。
- `KRS-E4406` 不在本 ADR 的範圍（第 8 節）。

### 決策點 8：與 ADR-0001、ADR-0003 的接點

本文件的畫面與這兩份 ADR **不是獨立的**（`docs/adr/README.md` 目前寫「0002 與另外兩份獨立」，需要由協調者更正）：

| 來源 | 會改變什麼 | 對本文件的畫面的影響 |
|---|---|---|
| ADR-0001（Windows 的版本槽） | 新的 `install.method = "slot"`；`slot` 主機不需要 `rollback_artifact`，預覽中不會列為「無法自動回滾」；可能新增 `install.upgrade` 的值 `insecure_path`；hello 的 `install.launcher`（「啟動器需要以 MSI 更新」）；移除「非 Linux 一律 `unsupported_platform`」 | 資格分類多出新的原因與安裝方式；現有字串「Windows 或不支援的平台（Windows 在 0.10 起）」會過時；「無法自動回滾」的說明不能寫成「deb／rpm 沒有舊版檔案」 |
| ADR-0003（`rollback_bundle`、本機封存） | deb／rpm 主機是否能自動回滾改由「本機紀錄 → bundle → 都沒有」決定；階段 2 的 hello `install.rollback` 與 Kairos 的資格分類 | `no_rollback` 的判斷與台數會變；S25 的「N 台主機的回滾需要這個版本」與「建議也匯入部署中的版本」的定義要重寫；L2 字串「升級 N 台（無法自動回滾 M 台）」的 M 會變（字串由伺服器計算，畫面不受影響） |

**留給它們的接點（本文件的實作就要做到）**

1. **原因代碼由資料驅動**：資格預覽、送審摘要、主機表以 API 回傳的原因代碼查字串；**不認得的代碼顯示為「其他原因（`<代碼>`）」**並照常列出台數與主機，不能讓畫面壞掉或把這些主機漏掉。安裝方式同理（不認得的顯示為「其他」，這是 `REMOTE.md` 第 2.1 節既有的規定）。
2. **所有台數與確認字串由伺服器計算**（`eligible`、`no_rollback`、`rollback_target_for`、`confirm_text`、`warnings[]`）；主控台不依安裝方式自行推算誰能回滾。
3. **文案不描述機制**：「無法自動回滾」的說明寫後果（「升級失敗時這些主機無法自動回到原本的版本，需要人工處理」），原因細節放在可展開的每一類說明中，由原因代碼決定；S25 寫「N 台主機依賴這個版本」而不是「N 台的回滾需要它的檔案」。設計包定稿時與 ADR-0001／0003 的核定結果對齊。
4. **篩選與摘要不以平台寫死**：S04 的「遠端升級」篩選、S05 的「升級」卡片、S26 的資格分類不假設「Windows＝不支援」。
5. 兩份 ADR 核定並實作時，各自的實作計畫要包含「更新 S25／S26 的字串與 Playwright 測試」；本文件的測試 E8 驗證接點 1。

## 4. 決策（建議）

1. **建立推送改為四步精靈**；草稿以明確的「儲存草稿」保存；`draft`／`pending_approval`／`scheduled` 的推送可以「修改…」。**修改功能與樂觀鎖（本文欄位 `expected_updated_at`）一起出貨。**
2. **核准為 L2「核准 N 台」，由伺服器計算確認字串與送審內容的 `digest`，並在核准的同一個交易中驗證**；沒有伺服器驗證就不出貨 L2。退回維持 L1＋原因。
3. **身分限制維持「建立者與送出者都不能核准」**，把因此產生的三人邊界寫進畫面、文件與測試；`approvers_available` 為 0 時事先警告。
4. **待核准**是 S26 清單的一個檢視；泡泡只計目前使用者可以核准的筆數，由後端計算。
5. **逾時**：期限在送出時固定、轉移等同系統執行的退回、以穩定的原因代碼保存、核准的交易也檢查期限；**與通知的系統規則一起出貨**。
6. **`rollout_approval`** 在 S21 唯讀顯示，0.10.0 維持只能在設定檔修改——**明列為治理缺口**；Kairos 保存前值、啟動時比對，`required` → `none` 在遠端管理開始接受請求前寫入稽核並開警告等級、預設推播的事件；部署文件列出補償措施；修訂 `REMOTE.md` 第 5.4 節。
7. **版本庫的檔案遺失**：採用整合分支已完成的 `file_problem` 與補檔；另外在預覽、送出、核准、提議四處檢查檔案，讓送審摘要可信。
8. **批次編輯器**採逐批欄位列；風險提醒由伺服器以固定代碼回傳，三個畫面顯示同一組。
9. **時段**：時段列加一週總覽；時區清單由伺服器提供；時段外的推送仍是「進行中」。**名稱待決（研究中）。**
10. **S25** 匯入時先選來源；資格預覽新增外部 URL 的兩類原因。**全域搜尋**的提示依可用的提供者組成。
11. **`KRS-W8417`** 建議照工程的號碼正式分配。`KRS-E4406` 不在本 ADR。
12. 畫面以資料驅動、容忍不認得的原因代碼與安裝方式，作為 ADR-0001、ADR-0003 的接點。

## 5. 後果

**正面**

- 第二人的確認由伺服器強制，並且綁定到一份可以事後證明的送審內容（`digest`）。
- 送審摘要的數字與實際會發生的事一致：檔案遺失的主機不再被算成可升級。
- 被退回的推送可以在主控台修改後重新送出；同時修改不會互相覆蓋。
- 雙人覆核被關閉時一定留下紀錄並通知；稽核員能在 S21 看到政策。
- 待核准的推送不會無限期佔住主機，也不會核准到過期的對象。
- 新的安裝方式與回滾機制上線時，畫面不需要重寫。

**負面與風險**

- **治理缺口仍在**：有主機權限的人可以獨自關閉雙人覆核。本文件只做到偵測與通知；阻止要靠部署端的流程或之後的方案 B。
- 兩位管理員的部署在「甲建立、乙送出」時無法核准（三人邊界）。
- 後端的工作量比初稿估計的大很多（核准的交易、`digest`、檔案檢查、逾時、前值保存、系統規則、schema 遷移），而且都是安全相關、需要仔細測試的程式。
- 核准 API 的請求內容改變（`confirm`、`digest` 成為必填）；雙人覆核尚未發佈，沒有相容問題，但 0.10.0 草稿的 CHANGELOG、`API.md`、`REMOTE.md` 要同步。
- schema 多三處變更（`approval_deadline`、`reject_cause`、政策前值），要併入整合分支重新編號的遷移。
- `pulse-rollout-new.js` 重構為精靈，`e2e-remote.mjs` 中建立推送的測試要改寫。
- 時段的名稱尚未定案；在定案前新增的字串都要集中，否則改名的成本會擴散。
- 設計包的規格與工程的實作會有一段時間不同步：工程以本 ADR 為暫行依據，設計包定案後需要一輪返工（已獨立列工）。

## 10. 尚未確認的事實

**已解決（相較於初稿）**

- `GET /api/v1/settings` 回傳 `remote.*`：已確認會回傳〔程式〕。
- `GET /api/v1/releases` 是否逐檔回報檔案遺失：整合分支已有 `file_problem`〔整合分支〕。
- 檔案遺失時的資格分類：已確認目前**不會**變成 `no_artifact`，主機仍算可升級〔程式、整合分支的 CHANGELOG〕。
- 樂觀鎖：已確認不存在〔程式〕。
- `KRS-E4406` 的使用範圍：已在整合分支確認（兩個命令），並已拆出本 ADR。

**仍未確認**

1. 推送是否記錄最後修改者（`updated_by`）；影響 2c 的補充與 409 `rollout_modified` 能否顯示「被誰修改」。
2. 刪除版本的保護（`release_in_use`）是否已涵蓋 `pending_approval` 與 `scheduled` 的推送（F6）。
3. 整合分支的 PostgreSQL 後端對推送狀態轉移的併發保證（交易隔離等級、是否有條件式更新或列鎖）；影響 A7。
4. 政策前值要放在哪一張表；資料庫中是否已有適合的鍵值表。
5. 可核准者的計算如何處理目錄服務的使用者（未登入過的不在本機資料中）。
6. 設計系統是否已有通用的步驟列元件（我只以關鍵字搜尋，沒有找到）。
7. IANA 支援上線後 `default_timezone` 與 `alerts.timezone` 的格式、tzdb 的來源與版本、DST 的語意（另一條線）。
8. 既有的遠端管理系統規則（`sys.rollout_paused` 等）的機制能否直接承載「預設推播的警告」與「接近期限時升級嚴重度」；需要告警線確認。
9. 估工是粗估，沒有逐項拆解驗證；後端的數字尤其取決於第 3、4、8 項的答案。
