## 2. 決策驅動因素

1. **避免誤操作造成大規模升級**：一次送出可能影響上萬台主機。對象、批次、時段要能在送出前一次看清楚，數字要與確認字串一致。
2. **權責分離**：開啟雙人覆核時，第二個人必須真的看到「被固定下來的內容」，而不是只按一個按鈕；一個人不能獨自繞過。
3. **可稽核**：送出、核准、退回、逾時、關閉雙人覆核都要留下紀錄，稽核員不需要讀設定檔就能知道目前的政策。
4. **與既有畫面一致**：沿用設計包的畫面編號、確認等級（L1～L3）、`impact_token`／確認字串、三段式錯誤文案、狀態詞彙與計數泡泡規則，不發明新的互動樣式。
5. **可及性**：WCAG 2.1 AA、axe 0 違規（淺色與深色）、全部可用鍵盤操作；狀態不能只靠顏色；即時更新用 `aria-live`。只支援 Chromium 系（D44）。
6. **實作成本**：主控台是原生 ES modules、沒有框架，嚴格 CSP 與 Trusted Types；優先重用 `pulse-rollout-new.js` 既有的欄位與預覽，不引入新的相依套件。
7. **API 相容**：0.9 的用法（省略 `waves`、`schedule`）不能變；需要新增的 API 欄位都是選用。

## 3. 決策點與方案

### 決策點 1：建立推送的形式、草稿的儲存與修改

**1a. 表單的形式**

| 方案 | 說明 | 優點 | 缺點 |
|---|---|---|---|
| A. 維持單頁表單加區塊 | 現況 | 不用改；一眼看到全部 | 0.10 之後有 30 個以上的欄位；資格預覽、批次台數、時段狀態混在一起，最容易出錯的「對象」與「批次」沒有被分開檢查；與設計包「0.10 改為精靈」不符 |
| B. 分步精靈 | 四步，最後一步是唯讀的檢視與送出 | 每一步只回答一個問題；最後一步把即將發生的事完整寫出來，也正好是核准者要看的內容，可以共用同一個元件 | 重構成本；步驟間切換要處理驗證與焦點 |
| C. 單頁＋區塊導覽＋固定摘要 | 單頁保留，左側加錨點、右側固定摘要 | 成本最低 | 沒有「檢視」這個強制停頓點；長頁面的錯誤摘要與焦點管理比精靈更難做好 |

**建議：B**。步驟如下（`REMOTE.md` 第 9 節 R6 是五步；建議把「目標版本」與「對象」合併，因為資格分類同時取決於兩者，分開會讓使用者在第二步才發現第一步選的版本沒有對應的發佈檔）：

| 步驟 | 內容 | 這一步的預覽 |
|---|---|---|
| ① 版本與對象 | 名稱、目標版本（`breaking` 的勾選、`min_kairos` 不相容的 `KRS-W8415`）、對象（全部，或群組／標籤／主機的聯集與排除）、選項「允許無法自動回滾的主機」「允許降版」 | 資格預覽：可升級 N 台，不會升級的依原因分列、每類可展開前 100 台；重疊的推送 |
| ② 批次 | 決策點 3 的批次編輯器、同時升級的上限、健康確認期限、離線寬限 | 每批的台數與累計 |
| ③ 時段 | 決策點 4：開始與結束時間、每週時段、時區；都不填＝立即開始、隨時可升級 | 現在是否在時段內、下一個時段 |
| ④ 檢視與送出 | 唯讀摘要（下稱「送審摘要」）：目標、對象的選擇條件與台數、每批台數與參數、時段、選項的風險標示、啟用雙人覆核時「送出後需要另一位管理員核准」 | 「送出推送…」開啟 L2／L3 對話框（確認字串由預覽的 `confirm_text` 提供，不變） |

互動規則：

- 路由：`/pulse/rollouts/new`（新增）與 `/pulse/rollouts/:id/edit`（修改），步驟以查詢參數 `?step=1…4` 表示，可以用瀏覽器的上一頁、可以貼網址。
- 步驟列是 `<nav aria-label="建立推送的步驟">` 內的有序清單，目前的步驟 `aria-current="step"`；已完成的步驟可以直接點回去，尚未到達的步驟不能跳過（`aria-disabled` 並說明原因）。修改既有草稿時四步都可以直接進入。
- 「下一步」時驗證這一步：有錯誤時在步驟頂端顯示錯誤摘要（`role="alert"`，逐項連到欄位）並把焦點移到摘要；切換步驟後焦點移到步驟標題（`h2`，`tabindex="-1"`）。
- 預覽沿用 600 ms 防抖與 `aria-live="polite"`（與 S24 相同）；預覽失敗時保留上一次的結果並標示「預覽不是最新的」。
- 步驟 ④ 進入時一定重新取一次預覽；與上一次的數字不同時顯示差異（「可升級台數由 1,520 變為 1,498」）。
- 設計系統目前沒有通用的步驟列元件規格（S02 首次啟動精靈各自描述）；需要設計包補上（第 6.1 節 #2）。

**1b. 草稿的儲存**

| 方案 | 說明 | 評估 |
|---|---|---|
| A. 只在送出時建立（現況） | — | 填到一半離開就全部遺失；被退回的推送無法修改 |
| B. 明確的「儲存草稿」 | 每一步都有「儲存草稿」；第一次 `POST`、之後 `PUT`；離開未儲存的精靈時詢問（`isDirty()`） | 行為可預期；稽核只有 `rollout.create`／`rollout.update`，次數少 |
| C. 自動儲存 | 每次切換步驟自動 `PUT` | 不會遺失，但會產生大量 `rollout.update` 稽核事件，還會留下許多沒有名稱的草稿 |

**建議：B**，並且在步驟 ④ 按「送出推送…」時先自動儲存（現況的行為）。草稿不固定對象、也不算在「未結束的推送」中，所以儲存草稿沒有副作用。

**1c. 修改**

- 入口：詳情頁在 `draft`、`pending_approval`、`scheduled` 狀態顯示「修改…」（`rollouts:write`）。
- `draft`：直接進入精靈。被退回的草稿在精靈頂端顯示退回原因（現有的 `reject_reason`）。
- `pending_approval`、`scheduled`：先以 **L1** 確認「修改會把推送退回草稿：已固定的對象會清除，需要重新送出（並重新核准）」，確認後才進入精靈；實際的退回發生在第一次儲存時（`PUT`），使用者在精靈中取消則什麼都不變。
- 清單新增「草稿」檢視（決策點 2a），空狀態與其他檢視分開。
- **並行修改**：`PUT` 目前沒有前置條件，兩位管理員同時修改同一份草稿時後寫的會蓋掉先寫的。建議 API 接受 `expected_updated_at`（不符時 409，主控台顯示「這份草稿已被 chen.y 在 10:32 修改」並提供重新載入）。這是小的後端變更，列入計畫。
- **放棄草稿**：API 沒有刪除，草稿以「取消推送…」（L1，原因必填）結束並留在「已取消」。對草稿而言原因必填偏重；建議草稿的對話框標題改為「捨棄草稿」、原因選填（後端對 `draft` 放寬），列為待決事項 U7。

### 決策點 2：雙人覆核

**2a. 待核准清單放在哪裡**

| 方案 | 說明 | 評估 |
|---|---|---|
| A. S26 清單的檢視 | 清單上方的檢視切換：進行中（預設）／待核准／草稿／已結束／全部，各附計數（與 S06 告警事件的檢視同一種樣式） | 推送本來就在 S26；不新增頁面與路由 |
| B. 獨立的「待核准」頁 | SideNav 另一個項目 | 與註冊的 S13「待核准」同名，容易混淆 |
| C. 併入 S13 | 把推送與註冊申請放在同一個待辦清單 | 兩者的權限、欄位、操作完全不同 |

**建議：A**。「待核准」檢視的網址為 `/pulse/rollouts?view=pending_approval`，欄位改為：名稱、目標版本、可升級台數、送出者、已等待多久、風險標示（降版、無法自動回滾、一次全部）。

**計數泡泡與通知**

- SideNav「升級推送」泡泡維持一個數字：已暫停＋未處理的回滾失敗＋**等我核准**的推送。現況把自己送出的也算進去，使用者點進去卻沒有可以做的事；建議只計「目前的使用者可以核准」的筆數（清單 `meta` 新增 `pending_approval_actionable`，或由主控台以 `created_by`／`submitted_by` 過濾）。可存取名稱要寫出組成，例如「升級推送，2 個待核准、1 個已暫停」。
- `design/kairos/ia.md` §7 補上這一列。
- 通知：目前送出者只能在系統外告知核准者。方案：(a) 只有泡泡與檢視；(b) 送出後的畫面提供「複製連結」；(c) 新增系統規則「升級推送等待核准」（資訊等級的紀錄事件，預設不推播，可接到通知管道，對象是有 `rollouts:approve` 的人）。**建議 (a)＋(b) 隨 0.10，(c) 列為後續**（需要告警線配合，待決事項 U3）。

**2b. 核准與退回的確認等級**

| 操作 | 方案 | 建議 |
|---|---|---|
| 核准 | L1（現況：一般確認）；或 **L2**：輸入「核准 N 台」（N 為已固定的可升級台數） | **L2**。核准是 N 台主機開始升級前的最後一道關卡，與送出（L2「升級 N 台」）對稱；輸入台數能迫使核准者看過數字。對話框內嵌「送審摘要」（與精靈步驟 ④ 同一個元件）。包含降版時為 L3：輸入「核准降版 N 台」＋原因必填，依 1.1 的定案**不**重新驗證密碼 |
| 退回 | L1，原因必填（現況） | 維持。退回往安全的方向，不需要更高的等級 |

- 依設計包的慣例，確認字串由伺服器驗證：建議 `POST …/approve` 接受 `confirm`（不符時 400 `confirmation_required`，與 `submit` 相同），並在推送的 JSON 提供 `approve_confirm_text`。後端完成前，主控台先在用戶端比對。
- 核准時 `starts_at` 已經過了：對話框明寫「核准後會立即開始升級」。`ends_at` 已過（409 `schedule_ended`）：就地說明並建議退回。

**2c. 送出者與核准者看到的差異**（詳情頁，`pending_approval`）

| | 送出者／建立者 | 其他有 `rollouts:approve` 的人 | 維運者、稽核員 |
|---|---|---|---|
| 頁首狀態 | 「待核准」＋「已在 11/12 10:05 送出，等待另一位管理員核准」 | 「待核准」＋「chen.y 在 11/12 10:05 送出，等你或另一位管理員核准」 | 「待核准」＋送出者與時間 |
| 主要動作 | 「修改…」「取消推送…」「複製連結」 | 「核准…」（主要）「退回…」 | 無 |
| 說明 | 「你建立或送出了這個推送，不能自己核准（`KRS-E6106`）」 | 送審摘要展開顯示 | 送審摘要 |
| 以 API token 操作時 | — | 「核准需要以帳號登入」（403 `session_required`） | — |

- 不能核准時「核准…」**不顯示**並以文字說明（現況；測試也依此）。這與設計系統「停用的元件要說明原因」不衝突，因為說明就在狀態橫幅內。
- 現況中送出者自己也看得到「退回…」（後端不限制身分）。對送出者而言「修改…」已經能把推送退回草稿，建議送出者的畫面不顯示「退回…」，避免兩個意思相近的動作；API 不變。

**2d. 退回原因與覆核紀錄**

- 退回原因必填、1～500 個字元，寫入稽核 `rollout.reject`，在草稿的頁首與精靈頂端顯示給建立者，再次送出時清除（現況）。
- 詳情頁新增「覆核紀錄」區塊，顯示目前這一輪的送出者／時間、核准者／時間或退回者／時間與原因（推送 JSON 已有 `submitted_*`、`approved_*`、`reject_reason`）。完整的多輪歷史在稽核日誌：對有 `audit:read` 的人提供「在稽核日誌查看」（帶入這個推送的篩選）。不為此新增歷史 API。

**2e. 逾時未核准**

現況沒有逾時：待核准的推送無限期佔住它的主機（其他推送會 `rollout_overlap`），而且核准的是幾天前固定下來的對象。

| 方案 | 說明 | 評估 |
|---|---|---|
| A. 不逾時，只顯示等待時間 | 清單與詳情顯示「已等待 3 天」；超過 72 小時在 S20「遠端管理」列為警告 | 不用改引擎；但過期的對象仍可能被核准 |
| B. 逾時自動退回草稿 | `[remote] rollout_approval_timeout_hours`（建議預設 168，範圍 1～720）；到期由 `system` 退回草稿，`reject_reason` 為「超過 7 天沒有核准，已自動退回」，稽核 `rollout.approval_expired` | 釋放主機、強迫以新的對象重新送審；需要後端 |
| C. 逾時自動取消 | 同 B 但轉為 `cancelled` | 建立者要從頭再建一次，沒有必要 |

**建議：B，並在 B 完成前先做 A 的顯示**。核准對話框一律寫出「對象在 N 天前（送出時）固定」。

**2f. `rollout_approval` 在 S21 的呈現，以及 `required` → `none`**

| 方案 | 說明 | 評估 |
|---|---|---|
| A. S21 唯讀顯示＋啟動時的稽核事件 | S21「連線與安全」分頁新增「遠端管理」卡片，列出 `[remote]` 的鍵；`rollout_approval` 顯示為「雙人覆核：需要／不需要」，來源標示「在 kairos.toml 修改，需要重新啟動」。Kairos 啟動時比對上一次記錄的值，改變時以 `system` 寫稽核事件（建議動作名 `settings.rollout_approval.change`，`details.from`／`to`）；由 `required` 變為 `none` 時另開一則資訊等級的紀錄事件「雙人覆核已關閉」 | 成本低；與 `REMOTE.md` 第 5.4 節「主控台唯讀顯示」一致；補上稽核的缺口 |
| B. 可從主控台修改 | 設定存資料庫、立即生效；`none` → `required` 為 L1，`required` → `none` 為 L3 且本身需要另一位管理員核准 | 最完整，符合 S21 原規格的「雙人覆核開關」；但 L3 的重新驗證目前不存在，且「關閉雙人覆核要不要雙人覆核」需要新的待辦流程 |
| C. 維持現況 | 只在 S20 的 `values` | 稽核員無從得知政策何時被關閉 |

**建議：A**。理由：修改 `kairos.toml` 並重新啟動需要主機上的系統權限，門檻不低於主控台的 L3，因此**在維持「只能在設定檔改」的前提下不需要另外的 L3 流程**；但它繞過了主控台的稽核，所以**稽核事件是必要的**。設計包 S21 的「雙人覆核開關」改為唯讀並註明；方案 B 列為後續（與其他操作的雙人覆核、L3 重新驗證一起設計，`INTEGRATION.md` §31.9）。

補充規則：由 `required` 改回 `none` 之後，已經在 `pending_approval` 的推送仍然要核准或退回（現況），S26 的「待核准」檢視在還有這類推送時繼續顯示。

### 決策點 3：自訂批次的編輯器

| 方案 | 說明 | 評估 |
|---|---|---|
| A. 逐批的欄位列 | 每批一個 `fieldset`：大小（單位可選「%」或「台」）、上限台數（百分比時）、觀察時間、失敗上限、人工繼續；最後一批固定為「其餘」 | 與 API 一一對應；鍵盤與螢幕報讀器最單純；延伸現有的做法 |
| B. 拖曳的比例條 | 以滑桿切分 100% | 看起來直覺，但百分比是「當時剩餘」而不是總數，比例條會誤導；拖曳的可及性成本高 |
| C. 只提供範本 | 兩批／四批擇一，不能自訂 | 不符合已實作的能力 |

**建議：A**，細節：

- **範本**：「套用範本」選單——兩批（預設）、建議的四批（1% → 10% → 50% → 其餘），內容取自預覽的 `wave_templates`。套用會取代目前的批次，已經手動改過時先確認（L1）。
- **第一批**稱為「先行批次」（設計包的用語；`canary` 只出現在技術細節）。來源二選一：「自動挑選」（依大小）或「指定主機」（`canary_agent_ids`，`Combobox`，只能選可升級的主機）。只有一批時不提供指定主機。
- **大小**：數值＋單位。百分比的說明固定寫在欄位下：「以這一批開始時**剩餘**的可升級主機計算，至少 1 台」。每一列右側顯示預覽算出的結果：「152 台（剩餘 1,520 台的 10%）· 累計 168 台」。
- **觀察時間**：以分鐘輸入（0～10,080），旁邊顯示換算（「＝ 1 小時」）。**失敗上限**：以百分比輸入（0～100，送出時換算為 0～1）；0 的說明「任何一台失敗就暫停」。**人工繼續**：核取方塊。
- **增減**：「新增批次」插在「其餘」之前，最多 `max_waves`（10）批，到上限時按鈕 `aria-disabled` 並說明；每批有「移除第 N 批」。不提供拖曳排序。
- **驗證（阻擋）**：數值範圍；批數 1～10；指定的先行主機不在可升級名單中。
- **提醒（不阻擋，警告樣式，並帶到步驟 ④ 的送審摘要與核准對話框）**：
  - 只有一批：「沒有先行批次：所有 1,520 台會在同一批升級。」
  - 第一批超過 10% 或 100 台：「先行批次偏大。」
  - 所有批次都不需要人工繼續且觀察時間為 0：「批次之間沒有停頓，等同一次全部升級。」
  - 某一批算出來是 0 台（剩餘不足）：「第 4 批沒有主機，會直接略過。」
- **批次摘要**：編輯器下方以文字清單列出每批的台數與參數；可以另外附一條分段的比例條作為輔助，但資訊必須完整存在於文字中（比例條 `aria-hidden`）。
- 詳情頁的批次時間軸已支援多批（`pulse-rollout.js` `renderWaves`），只需補上逐批的「人工繼續」「上限台數」顯示。

### 決策點 4：維護時段

**4a. 用語**

推送的時段是「允許**開始**替換的時間」，告警的「維護時段」是靜音。兩者同名會讓人以為設了推送的時段就會靜音、或以為要先建立告警的維護時段。方案：(a) 維持「維護時段」並在說明中區分；(b) 推送改稱「**升級時段**」。**建議 (b)**，由設計包在 `copywriting.md` §2.2 定案（待決事項 U4）。本文以下仍沿用 API 的說法稱「時段」。

**4b. 時區選擇（IANA）**

- 元件：`Combobox`，可輸入搜尋 IANA 名稱。清單最上方固定三項：Kairos 的預設（預覽的 `default_timezone`）、`Asia/Taipei`、`UTC`；其餘來自瀏覽器的 `Intl.supportedValuesOf('timeZone')`（Chromium 支援）。伺服器不接受的名稱由預覽回報就地錯誤，主控台不自行判斷合法性。
- 顯示依 `copywriting.md` §5.1：`Asia/Taipei（UTC+8）`。有日光節約時間的時區另加一行：「這個時區有日光節約時間：時段依當地時間計算，換季時不需要調整。」
- 既有以固定位移建立的推送照原樣顯示（`UTC+8`），修改時可以保留或改選 IANA 名稱。
- 預設值：Kairos 的預設時區。不採用瀏覽器的時區（§5.1：避免同一個單位的人看到不同的時間）。
- **開始與結束時間（`starts_at`／`ends_at`）以同一個時區輸入**，欄位標籤帶時區（「開始時間（Asia/Taipei，UTC+8）」）；同一個步驟只出現一個時區。清單與詳情仍依全站的顯示時區，與時段的時區不同時在時段摘要後註明「（時段時區：Europe/Berlin，UTC+1）」。
- 換季當天不存在或重複的當地時間如何解讀，由工程（IANA 支援的那條線）定義；主控台只需要在預覽回傳的「下一個時段」照實顯示。

**4c. 每週時段的編輯**

| 方案 | 說明 | 評估 |
|---|---|---|
| A. 時段列 | 每個時段一個 `fieldset`：星期（七個核取方塊）、開始、結束（`<input type="time">`） | 現況；與 API 一致；可及性好；但看不出一週的全貌 |
| B. 7×24 的格子 | 以滑鼠塗選 | 直覺，但鍵盤操作困難、無法表達任意的 `HH:MM`、跨午夜的歸屬不明顯 |
| C. 時段列＋唯讀的一週總覽 | A 再加上依星期排列的文字總覽 | 保留 A 的優點並補上全貌 |

**建議：C**：

- 星期提供快速選擇「每天」「平日」「週末」；一個都沒勾視為每天（API 的行為），介面上直接顯示為「每天」。
- 結束早於開始時自動標示「跨午夜：到隔天 05:00 為止（算在開始的那一天）」。開始與結束相同為錯誤。
- 最多 16 個時段；相連或重疊的時段在總覽中合併顯示，並提示「時段 1 與時段 3 重疊，會視為一段」。
- 一週總覽是文字清單（「週一～週五 01:00～05:00；週六 00:00～週日 06:00」），就是送審摘要與詳情頁使用的同一段文字（`scheduleSummary`）。
- **阻擋**：`ends_at` 早於開始或早於現在；排程中已經沒有任何可用的時段（預覽 `window.next` 為 `null` 且目前不在時段內）——現況只警告「送出後不會升級任何主機」，建議改為不能進入步驟 ④。
- **提醒**：每個時段都短於 30 分鐘（「時段很短，每個時段可能只來得及開始少數主機；已開始的會照常完成」）。

**4d. 目前是否在時段內**

- 精靈步驟 ③ 與送審摘要：一行狀態文字（`role="status"`），兩種寫法——「現在在時段內，到今天 05:00 為止。」「現在在時段外，下一個時段是 11/14（六）01:00。」
- 沒有設定時段時：「沒有限制時段：送出（核准）後隨時可以開始升級。」

**4e. 時段外的推送狀態文案**

- 推送的狀態維持「進行中」，**不**新增狀態、也不借用「已暫停」（暫停是需要人處理的狀況，會進計數泡泡；等待時段不是）。「下一步」欄與詳情頁首顯示：「等待時段 · 11/14（六）01:00 開始（還有 3 小時 12 分）」；之後沒有時段時「時段外，之後沒有可用的時段」（警告樣式）。
- 已排程：「已排程 · 11/15 01:00 開始」。
- 主機層級：`pending`＋`window_closed` →「未開始（等待下一個時段）」；超過 10 次仍未開始 →「已逾期（連續 10 個時段都沒有開始）」並提供「重試」；`expired`＋`rollout_ended` →「已逾期（推送已到結束時間）」。
- 時段結束時還在替換中的主機照常完成，詳情頁以一行資訊說明，避免被誤認為時段沒有生效。

### 決策點 5：外部 URL 的版本庫、檔案遺失、資格預覽

**5a. S25 匯入對話框**

現況是一個「外部 URL（選填）」欄位：填了與沒填的語意差很多（上傳的檔案是「存入」還是只「登記」）。建議改為第一步的來源選擇（單選）：「存放在 Kairos（預設）」／「外部 URL」，選外部 URL 才出現 `base_url` 欄位與說明：「Kairos 只保存 SHA256SUMS、簽章與清單。發佈檔仍要上傳一次以登記雜湊與大小，但不會保存；Kairos 不會連線檢查這個 URL。」

**5b. S25 清單與詳情**

- 清單：版本旁加標記「外部 URL」；平台與格式欄的每個檔案有四種狀態——已存入、已登記（外部）、待上傳、**檔案遺失／大小不符**（警告色＋圖示＋文字）。
- 詳情（外部 URL）：顯示 `base_url`，並提供可複製的 Pulse 設定片段（`upgrade.url_allowlist = ["https://…/"]`），因為這是外部 URL 推送最常見的失敗原因。
- 檔案遺失：
  - S25 頁首顯示 `KRS-W8417` 的三段式（決策點 7），主要動作「重新匯入 0.9.0…」直接開啟該版本的匯入對話框（同一版本已存在時只需要補上遺失的檔案，現有行為）。
  - 清單的列與詳情的檔案表標示遺失的檔案，以及「312 台主機的回滾需要它」。
  - S20「遠端管理」列維持現況（附「前往 Pulse 版本庫」）。
  - 建立推送的步驟 ①：選到有檔案遺失的版本時就地警告並連到 S25。受影響的主機在資格預覽中如何分類（是否歸入 `no_artifact`）需要工程確認（第 10 節）。
- 資料來源：`GET /api/v1/releases` 目前是否逐檔回報遺失尚未確認；建議 `artifacts[]` 新增 `problem`（`missing`／`size_mismatch`／`null`），S25 不必另外讀健康 API（也避免 `releases:read` 與健康 API 權限不一致）。

**5c. 資格預覽中「不允許外部 URL 的主機」**

Pulse 宣告就緒後，資格預覽新增兩類（原因代碼的名稱由工程定，以下是建議）：

| 原因（建議） | 顯示 | 處理方式（展開後） |
|---|---|---|
| `url_not_allowed` | 「不允許從這個外部 URL 下載」N 台 | 在這些主機的 `pulse.toml` 設定 `upgrade.url_allowlist`（附可複製的片段），或改用存放在 Kairos 的版本 |
| `url_not_supported` | 「Pulse 版本不支援外部 URL（需要 0.10 以上）」N 台 | 先以存放在 Kairos 的版本升級到 0.10 |

與其他原因一樣可以展開前 100 台。這兩類只在目標版本是外部 URL 時出現。

宣告就緒之前的過渡（0.10 現況）：目標是外部 URL 的版本時，資格預覽上方固定顯示資訊「Kairos 目前無法事先知道哪些主機允許外部 URL。不允許的主機會在推送中回報『已拒絕』，不計入失敗比例。」詳情頁的主機表把 `declined`＋`url_not_allowed` 顯示為「已拒絕（外部 URL 不在主機的白名單，`PLS-W8411`）」。

### 決策點 7：代碼（建議，最終由設計包定案）

分配規則（`design/design-system/copywriting.md` §3.1～§3.2、`design/decisions/INTEGRATION.md` §31.3）：號碼唯一、等級字母不影響號碼、兩端看得到同一個原因時鏡像同號、子類別依「誰處理、怎麼處理」歸類、發佈後不重用。慣例（§29.4 #1）：工程暫定的號碼符合規則時照用，避免多一次對照。

已核對設計包目前的總表：84xx 用到 8416、44xx 用到 4405，8417 與 4406 在兩端都沒有使用。

**`KRS-W8417` → 建議正式分配為 `KRS-W8417`（號碼不變）**

- 子類別 84「遠端升級」：版本庫是遠端升級的一部分，處理的人（管理員）與方式（重新匯入發佈）與 `KRS-E8413` 相鄰。只有 Kairos 端，不鏡像。等級 W：不影響正在執行的服務，但影響推送與回滾。
- 「檔案不存在」與「大小不符」建議同號，以「原因」區分（處理方式相同；比照 §29.4 #3 的判斷）。
- 三段式草稿：
  - 標題：Pulse 版本庫的檔案遺失：0.9.0 的 pulse-0.9.0-…-amd64.deb（312 台的回滾需要）
  - 原因：版本庫記錄這個發佈檔已經存入，但在 `data/releases/` 找不到它（或大小與記錄不符）。常見的原因是還原了備份——`kairos db backup` 不包含發佈檔——或檔案被手動移動、刪除。補回之前，使用這個檔案的推送與自動回滾無法取得它。
  - 處理方式：
    1. 取得同一個版本的官方發佈包，在「Pulse 版本庫」重新匯入這個版本（或執行 `kairos releases import <目錄>`）；只需要補上遺失或大小不符的檔案。
    2. 不再需要這個版本時可以刪除它（沒有推送使用、也不是任何主機的回滾目標時）。
  - 技術細節：`missing_files[]` 的 `version`、`filename`、`problem`（`missing`／`size_mismatch`）、預期的路徑 `<releases_dir>/<sha256>`；只檢查檔案是否存在與大小，不重算雜湊。
  - 呈現：S20「遠端管理」列、S25 頁首與檔案標記、`kairos releases list`。
  - 多個檔案時的標題：「Pulse 版本庫的檔案遺失：0.9.0 的 pulse-0.9.0-…-amd64.deb 等 3 個檔案」。

**`KRS-E4406` → 建議正式分配為 `KRS-E4406`（號碼不變）**

- 子類別 44「外部資料庫與資料遷移」：§31.3 設立 44 的理由就是「處理的人（DBA）與方式不同」，這個錯誤的處理方式正是改用 PostgreSQL 自己的工具。替代的歸類是 00（命令列參數）或 43（匯出、匯入與備份），但前者暗示使用者打錯參數、後者的處理方式不適用，都不如 44。只有 Kairos 端。等級 E：命令沒有執行。
- 三段式草稿（以 `kairos db backup` 為例）：
  - 標題：`kairos db backup` 不支援 PostgreSQL 後端
  - 原因：這台 Kairos 的資料存放在 PostgreSQL（`storage.backend = "postgres"`），這個命令只能操作 SQLite 的資料庫檔。沒有做任何變更。
  - 處理方式：
    1. 備份請使用 PostgreSQL 的工具：`pg_dump`、pgBackRest，或 `pg_basebackup` 加上 WAL 歸檔。
    2. 需要可攜的 SQLite 快照時，執行 `kairos db migrate --to sqlite:<檔案>`。
  - 技術細節：命令、`storage.backend`、結束代碼。
  - 同一個代碼的另一個情況（`kairos reports import`）：處理方式改為「先匯入到 SQLite，再執行 `kairos db migrate --to postgres`」。
  - 呈現：CLI 的 stderr；主控台沒有對應的畫面。
- 這個代碼屬於 PostgreSQL 開發線，本文件只提出號碼與文案的建議，並請設計包確認結束代碼（`cli-style.md`）。

**一併請設計包處理的既有代碼**

- `KRS-E6106`：說明與三段式改為「不能核准自己**建立或送出**的推送」。
- 403 `session_required`（以 API token 核准或退回）：建議不分配新代碼，在 `copywriting.md` §3.4 的協定錯誤碼對照註明「不對應產品代碼，主控台與 CLI 以一句話說明」；主控台本來就不會讓以 token 登入的工作階段出現核准按鈕。
- 本文件建議的新行為（逾時自動退回、雙人覆核設定變更）只有稽核動作與紀錄事件，**不需要新的錯誤代碼**。

## 4. 決策（建議）

1. **建立推送改為四步精靈**（版本與對象 → 批次 → 時段 → 檢視與送出），草稿以明確的「儲存草稿」保存，`draft`／`pending_approval`／`scheduled` 的推送可以從詳情頁「修改…」回到同一個精靈；後兩者先以 L1 說明會退回草稿。
2. **雙人覆核**：待核准的推送是 S26 清單的一個檢視，計數泡泡只計目前使用者可以核准的筆數；核准為 **L2「核准 N 台」**（降版為 L3 字串＋原因、不重新驗證），退回維持 L1＋原因；詳情頁依身分顯示不同的動作並新增覆核紀錄；逾時 7 天自動退回草稿。
3. **`rollout_approval` 在 S21 唯讀顯示**，維持只能在 `kairos.toml` 修改，不另設 L3 流程；但 Kairos 啟動時偵測到值改變要寫稽核事件，改回 `none` 時另開紀錄事件。
4. **批次編輯器**採逐批欄位列（百分比或台數、上限、觀察、失敗上限、人工繼續），附範本、每批與累計台數，以及不阻擋的風險提醒；提醒會帶到送審摘要與核准對話框。
5. **時段**：改稱「升級時段」以區別告警的維護時段；IANA 時區以 `Combobox` 選擇、開始與結束時間以同一個時區輸入；時段列加一週總覽；時段外的推送狀態仍是「進行中」，下一步顯示「等待時段」。
6. **S25**：匯入時先選來源；檔案遺失在 S25 的頁首與檔案列直接標示並提供重新匯入；資格預覽新增「不允許外部 URL」「Pulse 版本不支援外部 URL」兩類，宣告就緒前以固定的資訊說明。
7. **全域搜尋**的頂列文字改為通用，對話框的標籤依可用的搜尋提供者組成。
8. **代碼**：`KRS-W8417`、`KRS-E4406` 建議照工程的號碼正式分配，三段式草稿如決策點 7。

## 5. 後果

**正面**

- 送出前有固定的檢視步驟，送出者與核准者看到同一份送審摘要，數字與確認字串一致。
- 被退回的推送可以在主控台修改後重新送出，不必使用 API。
- 稽核員能在 S21 看到雙人覆核的政策，並在稽核日誌看到政策何時改變。
- 待核准的推送不會無限期佔住主機，也不會核准到過期的對象。
- 時段、外部 URL、檔案遺失三種「推送沒有動」的原因都能在畫面上直接看出來。

**負面與風險**

- `pulse-rollout-new.js` 需要重構為精靈，`e2e-remote.mjs` 中建立推送的測試步驟要跟著改寫。
- 需要數個小的後端變更（第 7.2 節的「後端」欄）；其中核准的 `confirm` 與草稿的 `expected_updated_at` 會改變 API 的請求內容（都是選用欄位，不破壞相容）。
- 核准改為 L2 會讓單純的核准多一次輸入；對只有兩位管理員的小型部署可能覺得繁瑣（這類部署通常不會開啟雙人覆核）。
- 「升級時段」的改名會動到 0.10 草稿的 CHANGELOG、`REMOTE.md` 與既有字串；必須在 0.10.0 發佈前定案，發佈後再改名的成本高很多。
- 逾時自動退回新增一個設定鍵與一個稽核動作，文件要同步（`REMOTE.md` 第 5.3、5.4、7 節，`API.md` 第 17.3 節）。
- 設計包的規格與工程的實作會有一段時間不同步：工程以本 ADR 為暫行依據先做，設計包定案後可能需要一輪文案與版面的調整。
